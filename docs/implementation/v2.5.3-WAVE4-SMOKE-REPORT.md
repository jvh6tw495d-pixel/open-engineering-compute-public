## Wave 4 acceptance analysis (added by Sonnet reviewer, post-run)

Live run: 2026-08-03, `scripts/hermes_supertest.py` against the real
Hermes CLI (`C:\Users\joaop\AppData\Local\hermes\config.yaml`), one fixed
scenario (`microgrid_multipperiod_bess_tou`, 6-period BESS/TOU LP,
oracle `min_tou_cost = 4.2825`) — this harness runs a single scenario per
invocation by design (`scripts/multiagent_with_without_oec.py`), not a
suite; it is not a truncated sample.

**Weak (`granite4:7b-a1b-h-64k`) narrates badly, AA stays correct — the
plan §8 acceptance case, confirmed:**
- `with_oec_raw`: `authoritative_answer.values.min_tou_cost = 4.2825`
  (matches the oracle exactly), while the host's own restated JSON claimed
  `min_tou_cost = 6.48` (host prose score 1/10, `host_corruption` verdict).
- `with_oec_agent`: same correct `4.2825` in `authoritative_answer`, while
  the host's restated JSON claimed `2.77` (host prose score 4/10,
  `host_corruption` verdict) — a *different* wrong number than the raw
  arm, underscoring that the corruption is host-narration noise, not a
  deterministic OEC-side error.
- This is the delta the plan asks to document explicitly: **a host reading
  `authoritative_answer` gets `4.2825` in both arms; a host reading its own
  restated prose would have reported `6.48` or `2.77` — both wrong.** The
  hardening is not hypothetical here; it reproduces on a real local model.

**Strong (`nvidia/nemotron-3-ultra-550b-a55b`) — mixed result, documented
honestly rather than smoothed over:**
- `without_oec` and `with_oec_raw` both hit `transport_failure`: the
  `hermes chat` subprocess exceeded the 120s `--timeout` before finishing
  (see verdict detail in "Per-run details" below). This is a transport
  outcome, not a correctness signal either way — the run plan called for
  `--timeout 120`; a longer budget would likely let these complete, since
  `with_oec_agent` (same model, same scenario) did finish inside 120s.
- `with_oec_agent` succeeded (`ok: true`) and `authoritative_answer`
  is exactly `4.2825` — the correct number, sourced from the envelope, not
  from prose.
- However this arm is *also* labeled `host_corruption`, and that label
  needs a caveat: the captured "host prose answer" for this run is not a
  restated numeric JSON at all — it is the literal `agent.default` tool-call
  arguments (`{"tool": "agent.default", "action": "call", ...}`). The
  harness's `extract_json` picked up the last JSON object in the Hermes CLI
  transcript, which in this run was the tool invocation itself, not a final
  answer the model produced afterward — most likely the model's session
  ended (or `--max-turns 40` was reached) before it printed a closing
  numeric summary, rather than the model actively fabricating wrong
  numbers the way granite4 did above. **This is not the same failure mode
  as weak-host corruption** — it is a harness-capture artifact on a
  transcript that never reached a final narrated answer — but the net
  effect for a host relying on prose-parsing would still have been "no
  usable number," which is exactly the scenario `authoritative_answer`
  is meant to make moot: the AA was available and correct regardless of
  whether the host ever finished narrating.
- Net: strong did **not** cleanly demonstrate "stays clean end-to-end" the
  way the plan's acceptance table phrases it (two of three arms hit
  transport timeouts before finishing), but the one arm that did complete
  shows the same pattern as granite4 — `authoritative_answer` correct and
  available independent of whatever the host's own transcript did or
  didn't finish saying.

issue (`--timeout` too tight for the strong model's tool-call turnaround
through Hermes), not an envelope/divergence defect — no code in
`src/oec/mcp/envelope.py` or `divergence.py` is implicated. Do not treat
this as a stop condition (plan §13); re-running `without_oec`/
`with_oec_raw` for the strong model with a longer `--timeout` is optional
follow-up, not a blocker for this closeout, since `with_oec_agent` (the
arm this hardening actually targets) already completed and returned the
correct `authoritative_answer`.
