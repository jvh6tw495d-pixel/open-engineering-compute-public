# OEC 3.3.1 release recovery plan

**Date:** 2026-08-06
**Status:** **executed → candidate `oec==3.3.1`** (see [3.3.1-RECOVERY-CLOSEOUT.md](3.3.1-RECOVERY-CLOSEOUT.md))
**Working baseline:** `b3ce64d` (3.3.0 internal) → recovery commit on branch head

## Why this plan exists

The repository head already moved beyond the old `v2.5.x` planning documents:

- `pyproject.toml` declares `oec==3.3.0`;
- recent commits added chemistry, multiphysics and THD capability;
- README, technical debt, publication docs and some release assumptions still
  describe earlier `v2.5.x` / `v3.1.1` states;
- a formal external review concluded the codebase is **not release-ready yet**,
  but does **not** need redesign - it needs integration and closeout.

This plan turns that review into an execution order for the current tree.

## Current observed conflicts

These are visible directly in the repo state today:

1. Package version is `3.3.0`, while docs still present older release status.
2. The last five commits are already in the `3.1.0 -> 3.3.0` line:
   - `d1b45de release(3.1.0): chemistry 2.8 + Scientific IR / Model Registry 2.9`
   - `b500665 docs+feat(3.1.1): restore Option A; 2.9 RC residual + chemistry skills`
   - `7fc31df docs(3.1.1): closeout + human publish runbook`
   - `c9ee71e feat(chemistry): complete foundation module (oec 3.2.0)`
   - `b3ce64d feat(3.3.0): multiphysics skills, THD, sequential chemistry network`
3. README still opens with `v2.5.1 refinement`.
4. `docs/implementation/technical-debt.md` still declares its current-state
   review at `oec==2.5.2`.
5. There is already a forward-looking `docs/implementation/v2.7-EXECUTION-PLAN.md`,
   but it assumes a stable `2.6.2` release baseline that is not the operative
   truth of the current branch.

## Objective

Produce a coherent release candidate from the current feature line by:

- restoring catalog integrity;
- aligning MCP/agent-first behavior with newly added domains;
- closing the release-quality gates;
- reconciling docs/version claims with the real code state;
- preparing one publishable candidate version.

## Release recommendation

Do **not** publish the current tree as `v3.0.0`.

Recommended path:

- treat `3.3.0` as an internal milestone already accumulated in the branch;
- fix the remaining blockers on top of it;
- publish the first coherent candidate as **`3.3.1`** unless scope expands again.

Reason:

- it matches the actual code line better than rolling back the numbering story;
- it avoids shipping a public `v3.0.0` tag that points to a tree whose package,
  docs and closeout artifacts are already narrating a later state.

## Execution phases

### Phase 0 - freeze scope and establish baseline

Goal:
stop drifting feature scope and define the candidate we are fixing.

Tasks:

- freeze new feature work on top of `3.3.0` until the recovery closes;
- identify which untracked/incubation artifacts stay out of release scope;
- record the baseline commit, package version and current known blockers;
- decide the target release label: `3.3.1` unless a new feature lands.

Acceptance:

- one explicit target version;
- one explicit candidate branch/head for the recovery effort;
- no further feature creep during recovery.

### Phase 1 - restore skill catalog integrity

Goal:
make the declared skill catalog actually load and execute as a product surface.

Tasks:

- fix non-registering manifests;
- close contract/audit failures for the newly added skills;
- close unit-schema errors for physical quantities and dimensionless fields;
- add at least one `Engine.run` path test for every newly added domain/skill family;
- verify that registry-visible skill count matches the filesystem inventory.

Acceptance:

- all intended skills register;
- no manifest/contract/unit audit errors remain;
- new domains are proven through the real registry/engine path, not only direct
  implementation calls.

### Phase 2 - align agent-first and MCP with the real catalog

Goal:
ensure `agent.default` and related agent-first surfaces understand the domains
that now exist in the repo.

Tasks:

- add routing/domain support for chemistry, multiphysics, thermal/mechanics/
  fluids/materials where appropriate;
- avoid semantically incorrect fallback to unrelated specialists;
- decide whether unsupported free-text should:
  - route to a generic deterministic execution path; or
  - return structured domain-scoped clarification/candidates;
- review the packaging/location of `agents/` for installable agent-first claims;
- expand installation smoke so it proves agent-first from outside the repo cwd.

Acceptance:

- no registered domain is inaccessible or misclassified because the router is outdated;
- agent-first behavior is honest for both explicit `skill_id` and free-text cases.

### Phase 3 - close release-quality gates

Goal:
make the branch reproducibly green by the same rules we would expect in CI or
publication.

Tasks:

- unify Ruff version/behavior across lockfile, local env and pre-commit;
- zero lint and formatting drift;
- keep mypy green;
- run/repair the relevant audit gates:
  - skill contracts
  - physical units
  - coverage thresholds for new modules
  - secret / dependency / security scans as applicable
- make auxiliary scanners robust to encoding/runtime issues.

Acceptance:

- quality gates are green in one reproducible environment;
- no gate is "green by accident" because it skipped or crashed.

### Phase 4 - reconcile documentation and structural memory

Goal:
make the narrative of the project match the actual branch state.

Tasks:

- update README status/version/capability claims;
- update technical debt current-state header and queue framing;
- reconcile skill inventory and codebase map;
- reconcile release docs / closeout docs / public-alpha procedure;
- refresh Graphify on the actual candidate commit;
- make package version, docs and proposed tag tell the same story.

Acceptance:

- a new reader can infer the current state correctly from docs alone;
- Graphify and release docs point to the same candidate state.

### Phase 5 - prepare the public candidate

Goal:
generate and validate the publishable tree, not just the incubation checkout.

Tasks:

- regenerate the public/release tree from the corrected candidate;
- rerun release gates inside that clean tree;
- verify install, CLI, MCP and selected agent-first smoke from that tree;
- review excluded files and publication contents;
- only then create tag/remote/publication artifacts.

Acceptance:

- publishable tree matches the intended release;
- install/run/smoke evidence exists for that tree, not only for the dev checkout.

## Priority backlog

### P0 - must close before any release claim

- Skill registration mismatches
- Skill contract audit failures
- Physical-unit/schema audit failures
- Missing engine-path tests for new skill families
- Router/domain mismatch for new chemistry/multiphysics capabilities
- Agent packaging/installability ambiguity
- Release narrative mismatch (`3.3.0` code vs `v2.5.1` / `2.5.2` docs)

### P1 - should close during the same recovery

- Ruff/pre-commit version drift
- Coverage measurement on newly added modules
- Graphify refresh for the actual candidate
- Public-tree validation refresh

### P2 - can remain explicit technical debt if honestly documented

- OS-level sandbox isolation
- REST/MCP auth and rate limiting
- deeper routing semantics/telemetry tuning
- broader release governance (remote/tags/public workflow)

## Practical next step

Start with **Phase 1**, not docs.

The first execution block should answer three questions with repo evidence:

1. Which skills are currently declared but not registering?
2. Which audit errors are real blockers versus stale tooling expectations?
3. Which new skills lack an `Engine.run`-level proof?

Once those are enumerated, we can turn Phase 1 into a precise fix list and
avoid doing documentation work on top of a still-broken catalog.

## Done means

The recovery is complete only when we can honestly say:

- the skill catalog is whole;
- agent-first/MCP claims match the actual domains shipped;
- quality gates are reproducibly green;
- docs and version claims match the branch;
- the release candidate tree is validated outside the dev checkout.
