## 2. Work completed

### 2.1 Baseline stabilization (`f7cbf0a`)

- made the `oec.core` domain-independence test deterministic by probing a
  fresh interpreter;
- improved installed-wheel diagnostics to preserve complete stdout/stderr;
- separated installed CLI/sandbox smoke from numerical-backend execution;
- reconciled the V3 plan with the shipped v2.0 Scientific Kernel;
- marked the v1.5 compliance matrix as a historical snapshot;
- created the Q0 Quantities inventory;
- consolidated the current technical-debt queue;
- rebuilt Graphify before construction.

### 2.2 Quantity API and dimensional contracts (`abb31c7`)

- retained `QuantityValue` as the single JSON DTO;
- added JSON-safe dimension and conversion APIs;
- added explicit add/subtract/multiply/divide operations;
- added typed `QuantityOperationError`;
- rejected incompatible dimensional operations;
- separated affine temperatures from delta-temperature intervals;
- allowed temperature conversion while rejecting ambiguous affine arithmetic;
- introduced `same_dimension` separately from direct convertibility;
- preserved original versus normalized input provenance;
- added a small immutable SI-2019 constants catalogue (`c`, `h`, `e`);
- added representation-only `Uncertainty` and `UncertainQuantity`;
- explicitly excluded general uncertainty propagation from v2.1.

### 2.3 Input and output enforcement

- dimensional validation now covers scalar and array quantities;
- central normalization converts scalar and array quantities to canonical
  units before execution;
- `ResultDimensionalValidator` is wired automatically for dimensional skills;
- declared physical outputs require an exact `{value, unit}` DTO;
- output units must match the declared canonical unit;
- malformed, non-finite, unknown-unit and noncanonical outputs fail closed;
- existing `ExecutionResult`, REST and MCP shapes remain unchanged.

### 2.4 Physical skill migration

The following experimental skills moved from bare physical numbers to
QuantityValue-only contracts and were bumped to skill version `0.2.0`:

- `energy.balance`;
- `energy.load_metrics`;
- `battery.soc_step`.

Their examples, implementations, schemas, tests and Energy Specialist demos
were migrated. Dimensionless fields such as SOC, efficiency and load factor
remain plain numbers with explicit dimensionless classification.

### 2.5 Automated authoring gate

`scripts/audit_physical_units.py` now checks physical skill schemas for:

- unclassified bare numeric fields;
- missing or invalid canonical units;
- malformed quantity contracts;
- undocumented dynamic-unit exceptions;
- explicit dimensionless classifications.

Current result:

```text
9 physical skills scanned
0 errors
```

This covers the six electrical skills plus the two energy skills and one
battery skill.

## 4. Corrections made after independent review

The review loop found and closed several nontrivial issues:

1. an early offset-unit check used a private Pint registry API; it was replaced
   with public Quantity behavior;
2. direct convertibility was incorrectly being used as same-dimensionality
   for uncertainty;
3. affine `degC`/`degF` uncertainty intervals are now rejected, while
   multiplicative `K`, `delta_degC` and `delta_degF` intervals are accepted;
4. the dimension string no longer exposes Pint's formatting directly; OEC
   sorts dimensions and renders exponents explicitly;
5. the first energy/battery proposal allowed transitional bare-number input;
   this was rejected because it violated the hard zero-bare-physical-number
   gate;
6. array quantities were initially not covered by central validation and
   normalization; both paths now handle them;
7. optional physical outputs that legitimately return `null` are respected
   when the output schema permits null;
8. existing electrical output schemas using `unit.const` are now enforced even
   without an explicit output `x-oec-unit`.

## 6. Next program steps toward v2.5

### Step A — close v2.1 release metadata

Deliver the nine closeout items above. This is the only authorized next step
before beginning the Math IR implementation.

### Step B — v2.2 Math IR foundation

Recommended order from the Opus review:

1. ADR and versioned Math IR schema;
2. closed Pydantic models for symbols, literals, quantities, expressions,
   equations, inequalities, objectives, constraints and assumptions;
3. structural and dimensional validation;
4. minimal Backend Capability Registry skeleton;
5. deterministic problem classifier;
6. linear compiler to OPS/HiGHS with parity tests;
7. scalar-equation compiler to SciPy root finding with parity tests;
8. experimental `mathematics.solve_ir`;
9. optional migration path for two existing skills;
10. no arbitrary Python or unrestricted `eval`.

Stop gate: do not call v2.2 complete until one LP and one scalar-root problem
execute exclusively through IR and match the existing governed paths.

### Step C — Verification and backend foundations

Do not create a wide set of new skills first. Establish:

- backend capability declaration;
- explainable backend selection;
- structured backend-unavailable outcome;
- pre-verification report;
- post-verification for convergence, residuals, violations and reproducibility;
- consistent `ScientificResult` adaptation.

Registry skeleton should precede stable compiler method selection.

### Step D — applied mathematics driven by evidence

Prioritize gaps that exercise shared infrastructure:

- least squares, condition and residual norms;
- regression, intervals and bootstrap;
- forecast baseline and backtest;
- dual/gap reporting and infeasibility explanation;
- uncertainty propagation only after its contract is validated;
- state-space/control and advanced risk methods only when they add golden
  coverage rather than catalogue count.

The former “15 new skills” target is not by itself a release criterion.

### Step E — v2.5 consolidation gate

v2.5 requires:

- v2.1 physical I/O contracts fully auditable;
- versioned Math IR with LP/root parity and migration tests;
- Backend Registry with explainable selection/fallback;
- structured pre/post VerificationReport on IR execution;
- SDK/CLI/REST/MCP conformance;
- canonical golden cases organized by behavior and failure mode;
- global coverage at least 85% and critical paths at least 90%;
- installation, security, typing and public API documentation gates;
- zero private business rules;
- no Physics-scale work before this gate.

The number “130 golden cases” must represent independent scientific cases,
not merely 130 files or duplicated parametrizations.

## 7. Risks to keep visible

- five-second cold SciPy imports can still be problematic on Windows for some
  skill manifests;
- no OS-level memory/network/filesystem isolation exists yet;
- REST/MCP have no authentication or rate limiting;
- `ProvenanceRecord` still permits untyped extra passthrough;
- `diagnostics_from_mapping` remains heuristic;
- no Backend Registry, general Math IR or formal VerificationReport exists yet;
- public GitHub release remains a separate strategic decision.
