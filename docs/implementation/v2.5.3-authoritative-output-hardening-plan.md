# v2.5.3 authoritative-output hardening plan

**Date:** 2026-07-31
**Status:** planning complete — ready to execute Wave 1
**Scope:** harden the host-facing OEC agent flow so weak local LLMs cannot corrupt authoritative numerical results after the solver already succeeded.
**Code baseline:** re-verified against `codex/oec-v2.5` @ `0493ee6` on 2026-07-31. All
file:line citations below were checked at that commit; re-check before executing if
the branch has moved.

## Problem statement

Recent stress and benchmark runs exposed a boundary the current `agent.default`
design does **not** yet close:

- OEC specialist agents and raw skills can compute the correct result.
- The hosting LLM can still misread, reformat, truncate, or overwrite the
  returned payload before presenting the final answer.
- In practice, some local models completed all three benchmark arms without
  transport failure but still returned numerically wrong final JSON, including
  corrupted aggregates, impossible SOC trajectories, and mismatches against the
  solver's own validated execution result.

This means the current router protects **method selection** and **backend
execution**, but not yet the final **host-consumption contract**.

## Goal

Make OEC the authoritative owner of numerical answers whenever a computation was
actually executed, so host models become optional narrators rather than trusted
reconstructors of the result.

At the same time, preserve the parts users actually want to read:

- how the problem was classified;
- which specialist was chosen;
- which method/backend was used;
- why that route was selected.

## Acceptance criteria

The hardening is done only when all of the following are true:

1. `agent.default` can return a stable machine-consumable
   `authoritative_answer` envelope for solved tasks.
2. The envelope shape is consistent across routed specialists and raw-skill
   execution paths.
3. A host integrating OEC can render the authoritative answer without asking an
   LLM to rebuild fields such as objective value, trajectories, feasibility, or
   reviewer outcome.
4. Divergence between a host-supplied `claimed_answer` and OEC's
   `authoritative_answer` can be detected deterministically. (OEC cannot see the
   host's rendered output; the claim must be passed in — see the Wave 2
   architectural correction.)
5. Regression tests cover at least:
   - correct routed optimization result;
   - correct raw optimization result;
   - malformed host rewrite detected as divergence;
   - ambiguous request still returns clarification rather than fake numerics.
6. A real weak-model smoke path shows one of these outcomes only:
   - exact authoritative answer surfaced; or
   - explicit structured clarification / structured failure.
7. Solved-task responses can also include non-authoritative explanation fields
   for:
   - `problem_classification`;
   - `method_summary`;
   - optional `narrative`;
   without allowing those fields to override the authoritative numeric payload.

## Root cause

The current system still mixes two different products in one response:

1. machine authority:
   `ExecutionResult`, validated OPS, solver status, input hash, reviewer output;
2. host narration:
   human-readable summary composed by a model sitting outside OEC.

That is safe only if the host is trusted to preserve structure exactly. Small
local models are not reliable enough for that.

## Opus review folded in

The current revision of this plan already incorporates the concrete issues an
independent Claude Opus review surfaced during the controlled benchmark pass and
the follow-up plan audit:

- the response surface is larger than it first looked:
  normalization must cover **nine** live shapes, not just routed-vs-direct;
- routed payloads cannot be normalized inside `_run_specialist_by_name`
  because the `agent.default` path recurses and would double-wrap;
- `ExecutionResult` itself cannot carry the new envelope fields, so authority
  must wrap it rather than mutate it;
- free-text applied mathematics is a special case because
  `MathRequestReport` exposes `min_execution` and `max_execution`, not a single
  `execution` field;
- divergence detection must compare against a caller-supplied
  `claimed_answer`, because OEC as an MCP server never sees the host's final
  rendered output unless the host sends it back explicitly;
- the benchmark layer must distinguish:
  - transport success;
  - OEC execution success;
  - host preservation of the authoritative answer.

No separate "Opus addendum" remains open at plan level. What is left is
implementation work.

### Verified response-shape inventory

The normalization surface is **nine distinct response shapes**, not the two or
three an earlier draft of this plan assumed. Any normalizer written against a
smaller set will silently drop authority on the paths it did not model.

|---|-------|-----------|-----------|----------------------|
| 1 | `needs_clarification` | `src/oec/mcp/discovery.py:139-172` (`build_clarification_payload`) | `src/oec/mcp/server.py:566-572` | none (by design) |
| 2 | `needs_more_information` | `src/oec/mcp/discovery.py:266-295` (`build_skill_suggestion_payload`) | `server.py:598`, `server.py:610`, `server.py:667` | none (by design) |
| 3 | `SpecialistReport` | `agents/optimization_specialist/specialist.py:29-54` | `server.py:589`, `server.py:591` (`execute_ops` / `run_demo`) | `execution` (nullable) |
| 4 | `SkillAgentReport` | `agents/common.py:13-30` | all 7 specialists' `demo_label` / `skill_id`+`inputs` paths | `execution` (nullable) |
| 5 | `MathRequestReport` | `agents/applied_mathematics/specialist.py:18-47` | `server.py:664` (`run_request`) | **no `execution` key** — `min_execution` + `max_execution` |
| 6 | `ReviewReport` | `agents/scientific_reviewer/reviewer.py:25-42` | `server.py:624-629` | **none at all** — only `passed` + `checks[]` |
| 7 | Router wrapper | — | `server.py:577-582` | nested: `result.<shape 3-6>` |
| 8 | Bare `ExecutionResult` | `src/oec/execution/models.py:46-66` | `server.py:759-762` (raw-skill dispatch) | *is* the execution (top level) |
| 9 | Structured error | — | `server.py:231-236` (`_error_result`) | none; `isError=True` |

Three structural facts that constrain the design:

- **`ExecutionResult` is `frozen=True, extra="forbid"`** (`src/oec/execution/models.py:49`).
  Envelope fields cannot be added *inside* it; they must wrap it.
- **`status` is already overloaded.** In shapes 1-2 it is a routing state
  (`"needs_clarification"` / `"needs_more_information"`); in shape 8 it is an
  `ExecutionStatus` member (`VERIFIED`/`VALIDATED`/…/`FAILED`). Any new `status`
  semantics must be scoped to agent tools only.
- **`result` is also already overloaded.** In shape 7 `payload["result"]` is the
  nested specialist report; in shape 8 `payload["result"]` is
  `ExecutionResult.result`, the numeric payload itself
  (`tests/integration/test_mcp_server.py:90` asserts exactly that). The envelope
  must therefore *not* claim `result` as a new top-level key name.

- `MathRequestReport.min_execution` / `max_execution` are already
  `model_dump(mode="json")` dicts (`agents/applied_mathematics/specialist.py:132-133`),
  not `ExecutionResult` objects — so an extractor over these shapes can work
  uniformly on plain dicts.

## Plan

### Phase 1 — authoritative answer contract

Add a stable top-level contract for solved tasks returned by `agent.default`
and compatible specialist paths:

```json
{
  "status": "ok",
  "router": "agent.default",
  "selected_agent": "agent.optimization_specialist",
  "problem_classification": {
    "domain": "optimization",
    "problem_class": "lp",
    "confidence": 0.94,
    "reason": "Detected explicit objective, linear constraints, and bounds."
  },
  "method_summary": {
    "specialist": "agent.optimization_specialist",
    "skill": "optimization.lp",
    "backend": "HiGHS",
    "review_applied": true
  },
  "execution": { "...ExecutionResult..." },
  "authoritative_answer_schema_version": "1.0",
  "authoritative_answer": {
    "kind": "optimization_result",
    "values": { "...host-safe final answer fields..." },
    "provenance": {
      "run_id": "...",
      "input_hash": "...",
      "solver_status": "optimal"
    }
  },
  "narrative": "optional"
}
```

Rules:

- `authoritative_answer` is the host-facing numerical truth.
- `problem_classification` explains what OEC thinks the problem is.
- `method_summary` explains what OEC actually did.
- `narrative` is optional and non-authoritative.
- if `authoritative_answer` exists, hosts should not recompute any numeric
  field from prose.
- explanatory fields may be shown to the user, but must never overwrite or
  "improve" values from `authoritative_answer`.

The example above is the optimization case. The envelope must hold for all
**seven** specialists currently exposed (`server.py:71-78`):
`agent.optimization_specialist`, `agent.scientific_reviewer`,
`agent.applied_mathematics`, `agent.time_series`, `agent.energy`,
`agent.control_dynamics`, `agent.finance_uncertainty` — plus the
`agent.default` router. Anywhere this document enumerates specialists, seven is
the current count; `agent.control_dynamics` and `agent.finance_uncertainty` were
added in v2.5.2.

### Phase 2 — response-shape normalization

Normalize routed and direct specialist outputs so callers do not have to know
whether a result came from:

- `agent.default`;
- explicit specialist call;
- `ops` execution;
- `skill_id` + `inputs`.

Required normalization:

- same location for `execution`;
- same location for `authoritative_answer`;
- same location for `problem_classification`;
- same location for `method_summary`;
- same `status` semantics **for agent tools only** — raw-skill dispatch (shape 8)
  keeps `status` meaning `ExecutionStatus` and is deliberately left untouched;
- same field names for `selected_agent`, `skill_id`, `notes`, and `narrative`.

This closes the current "result is nested differently depending on path" trap.

Normalization is **additive**: the existing `result` nesting for `agent.default`
(shape 7) stays, because 32 existing test assertions across `tests/` read
`payload["result"][...]`. Normalized keys are *mirrored* at the top level
alongside it, so no existing test needs editing.

### Phase 3 — host divergence detection

> **Superseded in part by the Wave 2 architectural correction below.** OEC
> cannot observe the host's final JSON from inside an MCP server; the host must
> pass its claim in as an argument (`claimed_answer`). The comparison rules
> below still stand — only the input channel changes.

Add a deterministic comparison layer for host integrations:

- if a host emits final JSON that disagrees with `authoritative_answer`, mark it
  as divergence;
- prefer the authoritative payload over the host rewrite;
- preserve the host text only as commentary.

Minimum checks:

- exact equality for booleans / statuses;
- tolerance-based comparison for numeric scalars;
- length and element-wise checks for trajectories;
- consistency between totals and trajectories where applicable.

### Phase 4 — fail-closed presentation mode

For computation-backed answers:

- success path:
  show `authoritative_answer` directly and optionally append
  `problem_classification` / `method_summary` / `narrative`;
- mismatch path:
  show `authoritative_answer` and attach a structured warning such as
  `host_output_diverged`;
- ambiguous path:
  return `needs_clarification`;
- invalid tool invocation path:
  return structured OEC error only.

This is the key product behavior change: no more "soft success" with corrupted
numbers.

### Phase 5 — benchmark and harness repair

Update the benchmark and stress harnesses so they validate the new contract
instead of only scraping free-form final JSON.

Priority fixes already known:

- update energy payloads to current `QuantityValue` contracts where needed;
- read routed optimization results from the normalized authoritative envelope,
  not ad-hoc nested locations;
- separate three verdicts in reports:
  - transport succeeded;
  - OEC solver succeeded;
  - host preserved authoritative output.
- distinguish "explained well" from "returned correct authoritative payload".

### Phase 6 — weak-model real smoke gate

Before calling this stable, rerun at least one weak local model and one strong
model across:

- `without_oec`;
- `with_oec_raw`;
- `with_oec_agent`.

Acceptance expectation for weak models:

- they may still fail `without_oec`;
- they may still produce poor prose;
- but when OEC solves successfully, the surfaced authoritative numeric payload
  must remain correct.

## v2.5.3 roadmap

### Wave 1 — contract and normalization

Goal:
define the stable response envelope and make routed/direct paths emit the same
structure across all nine shapes above.

#### Design decisions (fixed before implementation)

- **Wrap once, at the `call_tool` boundary** (`server.py:730-741`), *not* inside
  `_run_specialist_by_name`. That function recurses for the `agent.default`
  routed path (`server.py:576`), so assembling the envelope inside it would
  double-wrap.
- **New module `src/oec/mcp/envelope.py`**, pure functions over plain dicts — no
  new pydantic models, no imports from `agents/`. Keeps it unit-testable without
  an `Engine`.
- **Purely additive.** Keep the existing `result` nesting; mirror normalized keys
  at the top level. Target: zero edits to existing tests.
- **Leave raw-skill dispatch alone** (`server.py:759-762`). Adding `status: "ok"`
  there would collide with `ExecutionStatus`.
- **`authoritative_answer.values` is `execution.result` verbatim** in this wave —
  not a curated per-domain field list. Curated lists mean seven domains of
  hand-maintained mappings; that is a later wave, if ever.
- **Emit `authoritative_answer` only when `execution.status` is not `INVALID` or
  `FAILED`.** Otherwise omit the key entirely — absence is the signal, not a
  null.

### Wave 2 — fail-closed safeguards

Goal:
prevent host-side corruption from silently becoming the final machine-readable
answer.

#### Architectural correction: OEC never sees the host's final output

OEC is an **MCP server**. It observes tool calls, not the host's rendered
answer. A divergence checker that compares against "the host's final JSON" is
therefore *unreachable in-band from inside OEC* — there is no code path where
that string arrives. The plan's Phase 3 as originally written is not
implementable as stated.

What *is* implementable: **the host must volunteer its claim as an argument.**
That pattern already exists in this codebase — `agent.scientific_reviewer`
accepts `claimed_objective` / `claimed_solver_status` (`server.py:129-139`), and
`agent.default` already accepts the same two fields in its own schema
(`server.py:116-117`). Generalize that seed rather than building something new:

- add a `claimed_answer` (object) field alongside the existing `claimed_*`
  fields, compared against `authoritative_answer` by the same helpers;
- **do not add a new MCP tool.** `tests/integration/test_mcp_server.py:78`
  asserts `len(tools) == len(skill_ids) + 10` (8 agent tools + 2 discovery
  tools); a new tool breaks it and signals the wrong architecture besides;
- **do not build a standalone divergence module** disconnected from a tool
  boundary — it would have no caller.

Also: `_json_text` serializes with `json.dumps(..., default=str)`
(`server.py:226-228`), so datetimes, enums and any non-JSON-native value are
stringified on the way out. Divergence comparison must therefore compare
**post-serialization** values, not pre-serialization Python objects, or every
`started_at` will read as a mismatch.

Deliverables:

- `claimed_answer` field on `agent.default` / `agent.scientific_reviewer`;
- divergence checker utilities operating on post-serialization dicts;
- structured `host_output_diverged` warning shape;
- comparison helpers for scalars, booleans, vectors, and aggregate consistency.

Acceptance:

- a simulated corrupted `claimed_answer` is detected deterministically;
- authoritative payload still survives as the surfaced result;
- tool count unchanged (existing exact-count test still passes).

## Risks and non-goals

Not in scope for this plan:

- semantic perfection of free-text routing;
- making weak models mathematically strong without OEC;
- replacing reviewer logic;
- redesigning Hermes itself.

Main risk:

- if normalization is partial, hosts will keep depending on path-specific
  extraction logic and the same class of corruption will reappear.
- if explanation fields are not clearly marked non-authoritative, downstream
  hosts may still read prose-like fields instead of the authoritative payload.

## Definition of done

We can say this problem is fixed when a weak host model can no longer turn a
correct OEC solve into an incorrect final machine-readable answer.
