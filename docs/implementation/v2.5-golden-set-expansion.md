# v2.5 golden-set expansion — closing the "Golden set ≥130" gate item

**Date:** 2026-07-28
**Branch:** `codex/oec-v2.5`
**Scope:** one item of the v2.5 "Mathematics Complete" hard gate
(`docs/implementation/OEC_V3_IMPLEMENTATION_PLAN.md` §9, V3 §16) — the
golden-set size and distribution. This is not a v2.5 closeout: see
`docs/implementation/v2.1-delivery-status-and-v2.5-next-steps.md` for the
full gate checklist and what else remains (public-API docs, defined
"critical path" coverage, the `forbidden_names` doc fix, etc.).

## 1. What was measured before this slice

A repo-wide audit (two independent Explore passes) found **142** golden
`def test_...` functions total, verified via `grep -c "^def test_"` across
every `tests/test_golden.py` (no file in the repo uses parametrization for
golden cases, so 1 function = 1 independent case — no double-counting).
The distribution against the V3 plan's required per-domain minimums:

| Domain | Minimum | Before | Status |
|---|---|---|---|
| Álgebra e cálculo | 20 | 46 | met |
| Probabilidade e estatística | 20 | 15 | **short by 5** |
| Séries temporais | 20 | 17 | **short by 3** |
| Otimização | 20 | 17 | **short by 3** |
| Incerteza | 10 | 7 | **short by 3** |
| Dinâmica | 10 | 3 | **short by 7** |
| Controle | 10 | 2 | **short by 8** |
| Validação e falhas | 20 | 0 | **did not exist as a bucket** |

The total (142) already exceeded 130, but the V3 plan is explicit that the
number must reflect real per-domain distribution, not just a raw count —
so the gate was not met despite the aggregate looking sufficient.

## 2. What changed

No new skills, no schema/behavior changes. Every new case is closed-form,
exact-arithmetic, or cross-checked against `scipy.stats`/`math` at test
time — the same convention the existing ~110 cases already use
(`src/oec/validation/golden.py`'s `GoldenCase`/`assert_matches_golden`, or
a bare `implementation.execute()` + `assert`/`math.isclose`).

|---|---|

### 2.2 New "Validação e falhas" bucket

**New file:** `tests/golden/test_validation_and_failures.py`, 22 cases.
Every case drives the real, sandboxed `ExecutionService` end to end
(registry → validators → subprocess → status → provenance) — the same
pattern as the existing `tests/integration/test_<skill>_end_to_end.py`
files — and asserts the resulting `ExecutionStatus` for a deliberately bad,
real input. Nothing is mocked.

| Mechanism | Cases | Skills exercised |
|---|---|---|
| Non-convergence → `INCONCLUSIVE` | 5 | `mathematics.curve_fit`, `.integrate`, `.optimize_scalar`, `.optimize_constrained`, `.solve_root` |
| Solver infeasibility → `INCONCLUSIVE` | 2 | `optimization.lp`, `.check_feasibility` |
| Linear-algebra domain validation | 3 | `linear.solve_system` (singular), `.eig` (non-square), `.least_squares` (dimension mismatch) |
| Physical validation → `INVALID` | 2 | `battery.soc_step` (soc out of range; negative capacity) |
| Dimensional validation → `INVALID` | 2 | `energy.balance`, `battery.soc_step` (unit-family mismatches) |
| Mathematical/expression validation → `INVALID` | 2 | `mathematics.optimize_constrained` (undeclared variable), `.solve_root` (newton without derivative) |
| Schema validation → `INVALID` | 6 | `linear.eig`, `uncertainty.morris`, `statistics.regression`, `energy.balance`, `optimization.lp` (extra field), `battery.soc_step` (missing required field) |

**One notable finding surfaced by writing these end-to-end (not just at the
implementation level):** `linear.solve_system`'s manifest declares
`method.iterative: false` (it's a direct LAPACK solve). Per ADR 0007, the
top-level `ExecutionStatus` only consults `diagnostics.converged` for
*iterative* methods — so a singular-matrix input, even though the
implementation correctly reports `singular: true` / `diagnostics.converged:
false` in its own result payload, still surfaces as `ExecutionStatus.
VERIFIED` at the service level, not `INCONCLUSIVE`. This is existing,
intentional ADR 0007 behavior (not something this slice changed), but it
means a caller relying on top-level status alone would miss a degenerate
solve on this specific skill — the test now documents this explicitly
(`test_solve_system_singular_matrix_reports_singular_not_an_exception`)
rather than silently asserting the status callers might expect.

### 2.3 Explicitly deferred — not attempted this slice

Flagged during the audit as needing real design work, not a quick port.
Recorded here as known, documented gaps rather than silently dropped:

- **`ExecutionStatus.APPROXIMATE`** — no code path in `compute_status`
  (`src/oec/execution/status.py`) ever returns it today. A real case
  cannot be written until something (truncated series, linearization,
  coarser-than-requested tolerance) actually produces it.
- **`KalmanNumericalError`/`innovation_singular`** — triggering the
  specific branch in `src/oec/kernel/control/kalman.py` needs more
  numerical care than a one-line input (most naive attempts get caught
  earlier by the PSD/symmetry pre-checks instead).
- **`invariants.py`'s non-finite-output check** — has never been
  triggered by any real skill in the suite; most division paths are
  already guarded upstream by `require_positive` or similar.
- **A genuinely-occurring `ExecutionStatus.FAILED`** on a real
  (non-fixture) skill — today only proven against fixture skills in
  `tests/unit/test_execution_service.py`.
- **`VerificationReport`'s `residuals_and_conditioning`/`backend_fit`
  post-checks** — never exercised against a real skill that genuinely
  reports a high condition number or residual.

Plus 35 golden cases in domains outside the V3 plan's 8-bucket accounting
(electrical 26, energy 4, battery 2, finance 3) — grand total **193**
golden `def test_...` functions in the repo.

Every required bucket now meets or exceeds its V3-plan minimum. Full suite:
1257 → 1308 tests passed (`-m "not slow"`; 51 new tests: 29 appended across
the ten small-gap files + 22 in the new failure-modes file); coverage rose
from 90.70% to 90.83% (no regression). `ruff check`, `ruff format --check`,
and `mypy --config-file=pyproject.toml` all clean on every touched file.

## 4. What this does NOT close

This slice is scoped to the golden-set size/distribution item only. Still
open from the broader v2.5 gate (per
`v2.1-delivery-status-and-v2.5-next-steps.md` §6 Step E):

- 100% public-API documentation audit.
- A defined, measured "critical path" coverage figure (≥90%) distinct from
  the current global-only 90%+ number.
- The one-line `forbidden_names` fix (`docs/implementation/
  v2.4-team-brief.md:7` uses the term "Horizon").
- Reconciling `docs/implementation/technical-debt.md`, which has not been
  updated since `oec==2.1.0` despite v2.2–v2.5 work since landing.
- The package version, `CHANGELOG.md`, and any release/tag decision —
  deliberately untouched here, consistent with this project's practice of
  only writing versioned changelog sections at formal release closeout.
