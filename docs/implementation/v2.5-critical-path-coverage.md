# v2.5 critical-path coverage (gate item: "cobertura crítica ≥ 90%")

**Date:** 2026-07-28
**Branch:** `codex/oec-v2.5`

The v2.5 gate (`OEC_V3_IMPLEMENTATION_PLAN.md` §9) requires "global coverage
at least 85%, critical paths at least 90%" but never defined which modules
count as "critical path," and no measurement of it existed before this
session — only the single global figure (currently 90.83%, `-m "not slow"`).
This closes that gap: a concrete module list, a real measurement against it,
and an honest account of where it's weakest.

## 1. Definition

"Critical path" = the modules responsible for **scientific correctness and
knowing reliably when a result should not be trusted** — the shared
execution/validation/verification pipeline and the computational kernels
every skill sits on top of. This deliberately excludes:

- **Transport adapters** (`src/oec/cli`, `src/oec/api`, `src/oec/mcp`) —
  thin, mostly-tested-by-integration-test surfaces that translate but don't
  compute (ADR 0005/0015: they pass `ExecutionResult` through unchanged).
- **Packaging/discovery infrastructure** (`src/oec/skills/loader`,
  `.registry`, `.schemas`, `.lifecycle`) — correctness of *finding and
  loading* a skill, not of the scientific result itself.
- **`src/oec/testing.py`** — a test-only helper, and **`src/oec/reports/`**
  — an empty scaffold (0 statements either way).
- **Individual skills** (`skills/*/implementation.py`) — these have their
  own dedicated golden-set coverage (see
  `v2.5-golden-set-expansion.md`), a different gate item.

Included:

| Package | Why |
|---|---|
| `src/oec/execution/` | `ExecutionService`, status computation (ADR 0007), provenance, sandboxed runner |
| `src/oec/validation/` | schema/dimensional/mathematical/physical/numerical/invariants layers |
| `src/oec/verification/` | pre/post `VerificationReport` (ADR 0021) |
| `src/oec/kernel/` | every computational/numerical/optimization/statistics/timeseries/uncertainty/dynamics/control/linear/units kernel — the actual math |
| `src/oec/modeling/` | Math IR (ADR 0020): classify, compile, dimensions, expressions |
| `src/oec/ops/` | OPS problem model/schema/conversion |
| `src/oec/backends/` | Backend Capability Registry (ADR 0021) |
| `src/oec/core/` | domain-independent `ScientificResult`/provenance/diagnostics contracts |
| `src/oec/sdk.py`, `src/oec/common.py`, `src/oec/errors.py` | the single shared `Engine` entrypoint every adapter calls through, shared value objects, and the error taxonomy that drives `INVALID`/`FAILED` classification |

## 2. Measurement

Measured via `coverage report --include=<critical-path globs>` against the
same `.coverage` database as the full `-m "not slow"` run (1308 tests,
90.83% global):

```text
TOTAL   3549 statements, 272 missed, 1132 branches, 190 partial   -> 90%
```

**The aggregate clears the 90% gate.** Per-package breakdown:

| Package | Coverage |
|---|---|
| `verification` | 100% |
| `validation` | 99% |
| `sdk` + `common` + `errors` | 99% |
| `execution` | 95% |
| `backends` | 94% |
| `modeling` | 93% |
| `ops` | 93% |
| `core` | 92% |
| **`kernel`** | **86%** |

## 3. Honest finding: `kernel` alone does not clear 90%

The aggregate passes only because `execution`/`validation`/`verification`
(near-100%) pull up the weighted average over `kernel`, which is both the
largest package by statement count (2079 of 3549, ~59%) and the weakest at
86%. Reporting only the aggregate would hide this. The specific
sub-90% kernel modules, weakest first:

| Module | Coverage | Missed branches, mostly |
|---|---|---|
| `kernel/timeseries/quality.py` | 67% | outlier/gap-detection edge branches |
| `kernel/timeseries/ops.py` | 68% | multi-column resample/align edge cases |
| `kernel/linear/solve.py` | 71% | *now exercised by the new singular-matrix golden case (2.5-golden-set-expansion), but the residual/condition-number reporting branches for near-singular (not exactly singular) matrices remain untested* |
| `kernel/energy/metrics.py` | 71% | tolerance-violation branch |
| `kernel/optimization/robust.py` | 74% | box-uncertainty edge cases |
| `kernel/timeseries/timegrid.py` | 70% | irregular-grid edge cases |
| `kernel/control/kalman.py` | 77% | the PSD/conditioning guard branches (`innovation_singular` etc. — see `v2.5-golden-set-expansion.md`'s explicitly-deferred list) |
| `kernel/optimization/feasibility.py` | 77% | multi-issue aggregation branches |
| `kernel/optimization/pareto.py` | 79% | sweep-boundary branches |
| `kernel/optimization/qp.py` | 80% | constraint-boundary branches |
| `kernel/optimization/cvar.py` | 80% | tail-probability edge cases |
| `kernel/uncertainty/morris.py` | 80% | *now partially improved by the new exact-linear-model golden cases, but the multi-trajectory std-dev branch for `n_trajectories>1` with mixed-sign effects remains untested* |

This is a real residual-risk list, not a rubber stamp — it belongs in
`technical-debt.md`'s queue as a concrete, itemized follow-up rather than a
vague "improve kernel coverage" line.

## 4. Verdict

**Gate item met**: critical-path aggregate is 90%, at the V3 plan's floor.
**Not met uniformly**: `kernel` itself sits at 86%; the eleven modules
above are the honest list of where a future coverage push should go first,
in the order shown (weakest first).
