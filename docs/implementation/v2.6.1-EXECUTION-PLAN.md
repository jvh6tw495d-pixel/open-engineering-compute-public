### D3 — Nomenclatura SOC: **energy-based**, não coulomb-counting — **FECHADO**

**Problema (Codex):** `soc_update` em `src/oec/kernel/energy/metrics.py` (~L32–69) integra **potência × tempo / capacidade** (= **energy counting**), não coulomb-counting por corrente/Ah. O docstring actual do kernel diz “Coulomb-counting” de forma **imprecisa**.

| Nome / conceito | Significado | Veredito |
|-----------------|-------------|----------|
| **`energy_based_soc_update`** | ΔSOC a partir de potência×tempo×η / capacidade energética | **Canónico em `oec.physics.storage`** e na documentação 2.6.1 |
| `soc_update` (kernel) | API legada **intocada** em código nesta release; docs/parity referem-na como **energy-based** | Wrap/adapter sem rename breaking do símbolo kernel em 2.6.1 (debt: alinhar docstring kernel em PR docs-only ou patch futuro) |
| **`coulomb_counting`** | Métodos por **corrente / Ah** (∫I dt / Q) | **Reservado** — **não** usar para o path potência×tempo; fora do mínimo 2.6.1 salvo input de corrente explícito futuro |

**Acção no plano:** corrigir toda menção a “coulomb-counting” para BESS 2.6.1 → **energy-based SOC**. Referência factual: `metrics.py` L41–44 (docstring) + integração L55–60.

### D4 — Grid-zero: **duas entregas distintas** — **FECHADO**

**Problema (Codex):** “min storage p/ autonomy” **não** é helper analítico puro — vira problema temporal/otimização; misturá-lo com feasibility contamina a fronteira com `optimization.lp`.

| Entrega | Tipo | Onde vive | Contrato |
|---------|------|-----------|----------|
| **`grid_zero_feasibility`** | Avaliação **determinística** de uma **trajectória fornecida** (séries load/pv/storage/grid já dadas) | `oec.physics.grid_zero` + skill `energy.grid_zero_feasibility` | Inputs: trajectórias; outputs: factível?, deficit por período, residual de balanço, flags; **sem** solver; **sem** HiGHS |
| **`min_storage_capacity`** | **Problema de optimização** (horizonte, curtailment opcional, η_c/η_d, limites SOC) | Skill `energy.min_storage_capacity` (ou nome estável) que **compõe** `optimization.lp` / Optimization Specialist | Physics **não** embute LP; formula o modelo (variáveis/constraints/objectivo) e chama o path de optimização existente |

**Fronteira com `optimization.lp` (contrato):**

1. Physics pode expor **helpers de residual / feasibility / défice** e builders de **dados de instância** (coeficientes, bounds) se reutilizáveis e determinísticos.
2. **Qualquer** minimização de capacidade / dispatch óptimo / sizing → **Optimization Specialist + skill optimization path**, não `oec.physics.*` a chamar HiGHS directamente.
3. Smoke W3: pelo menos um exercício de **feasibility** (physics) e, se calendário, um de **min capacity** via LP; feasibility **não** conta como “resolveu sizing”.
