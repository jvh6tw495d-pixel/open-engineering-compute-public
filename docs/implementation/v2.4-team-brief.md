# Team brief — OEC **v2.4** Computational + Verification + Backend Registry

**Lead:** Grok (validation) / construction agents as assigned
**Date:** 2026-07-27
**Baseline:** **`oec==2.3.0` ACCEPTED** on `codex/oec-v2.5` (seal: [v2.3-accepted-and-merge-prep.md](v2.3-accepted-and-merge-prep.md))
**Plan source:** [OEC_V3_IMPLEMENTATION_PLAN.md](OEC_V3_IMPLEMENTATION_PLAN.md) §8
**Horizon:** 6–8 weeks (V3 estimate; slice further if needed)

## 1. Why v2.4 next

v2.3 closed **applied skill volume** (Waves A+B+C + scientific corrections).
The next value jump is **not more isolated skills** — it is **formal pre/post verification**, a **backend capability registry**, and a thin **computational kernel refactor** so Math IR (v2.2) and applied paths (v2.3) compose under one governance surface.

```text
v2.2 Math IR foundation ──┐
v2.3 Applied Math        ──┼──► v2.4 Verification + Backends + computational unify
                           └──► v2.5 Mathematics Complete (hard gate)
```

## 3. Scope (in)

### 3.1 Verification Engine (core of the release)

| Phase | Checks (minimum viable) |
|---|---|
| **Pré** | symbols/inputs present; units/domain; contradictory constraints (when declared); missing required data; backend fit vs skill declaration |
| **Pós** | convergence flags (when method iterative); residual/violation summaries; LP gap when applicable; conditioning notes where cheap; reproducibility fields already present (`run_id`, `input_hash`) |

**Contract rule:** structured **Verification report** available on every successful execution path (SDK first; REST/MCP may expose as additive field or nested diagnostics — **must not break** existing `ExecutionResult` required shape).

### 3.2 Backend Registry

Target layout (from V3 §8):

```text
src/oec/backends/
  registry.py
  capabilities.py
  selection.py
  fallback.py
  adapters/          # thin wrappers / capability declarations
```

| Backend | Minimum capability flags |
|---|---|
| NumPy | dense linear algebra, RNG (declared) |
| SciPy | roots, integrate, interpolate, optimize, ODE (as used today) |
| HiGHS (`highspy`) | LP/MILP; optional extras path |
| (later) SymPy / JAX | **optional extras only** — not core deps |

**Fallback policy (v2.4):** if declared backend missing → **INVALID / clear error** (no silent solver swap that changes numerics). Documented table in docs + code.

### 3.3 Computational (bounded)

| Item | v2.4 expectation |
|---|---|
| root / interp / diff / int / ode | Unify under `kernel/computational` **or** documented package map — no LAPACK reimplementation (ADR 0008) |
| sparse | optional `scipy.sparse` path **only if** a skill needs it |
| symbolic | SymPy wrappers only if gated experimental skill |
| autodiff | JAX **optional extra** — do not force into core |
| DAE v0 | **at most one** experimental skill if SciPy path is stable; else defer |

## 4. Scope (out)

- New large applied skill waves (that is residual polish → v2.5, or physics → v2.6+)
- Certified IIS / full Sobol / black-box SA (accepted residuals from v2.3)
- Physics / chemistry complete
- Public GitHub publish (v3.0)
- Breaking REST/MCP/`ExecutionResult` required fields
- Reimplementing SciPy/NumPy/HiGHS numerics inside OEC

## 5. Definition of Done — gate v2.4

- [ ] `VerificationReport` (or equivalent structured object) produced on execute paths used by SDK
- [ ] Backend registry lists numpy / scipy / highs (+ optionals) with **capabilities**
- [ ] Selection + fallback documented; missing HiGHS → clear INVALID (no silent wrong engine)
- [ ] Provenance continues to list backends used (ADR 0017); registry is the source of capability truth
- [ ] Computational map refactored **or** explicitly deferred items listed in release notes
- [ ] Tests: unit + integration for registry selection and at least one pre + one post verification path
- [ ] Gates green: ruff, mypy, pytest (≥ 90% coverage policy unchanged), skill/units/forbidden audits
- [ ] Version **2.4.0** (or 2.4.0a0 → 2.4.0 if sliced) + CHANGELOG + README + V3 executive status
- [ ] `ExecutionResult` / REST / MCP **unbroken**

## 6. Suggested work slices (order)

| Slice | Name | Outcome |
|---|---|---|
| **S0** | Inventory | Doc: current validators vs Verification V3 gaps; current `backends[]` provenance vs registry |
| **S1** | Backend registry MVP | `registry` + `capabilities` + tests; HiGHS optional path |
| **S2** | Verification pré MVP | structured pre-check report; wire into execution factory without shape break |
| **S3** | Verification pós MVP | convergence/residuals/gap hooks where data already exists |
| **S4** | Computational unify (optional if S1–S3 slip) | package map + one migration PR |
| **S5** | Release seal | version, CHANGELOG, gates, local tag `v2.4.0` |

Prefer **S1 → S2 → S3** over deep computational refactor if calendar pressure.

## 7. Forbidden

- Silent backend fallback that changes answers
- Claiming “full formal verification” without pre **and** post structure
- Pulling JAX/SymPy into required core dependencies
- Private product names / forbidden tokens (run `check_forbidden_names.py`)
- Push to public remote without explicit human authorization
- Amending or force-pushing published history without request
